# Contributing to @peculiar/ssh

Thank you for your interest in contributing to `@peculiar/ssh`! This document describes how to set up the project, which checks a change must pass, and how releases are made.

## Development Setup

### Prerequisites

- Node.js `^22.18.0 || ^24.11.0 || >=26.0.0` for development (required by tsdown and Vitest; CI uses Node.js 24). The published package supports Node.js `^20.19.0 || >=22.12.0`.
- npm (the repository is locked with `package-lock.json`)
- OpenSSH `ssh-keygen` on the `PATH` for the compatibility specs (`*.compat.spec.ts`)

### Installation

```bash
git clone https://github.com/PeculiarVentures/ssh.git
cd ssh
npm ci
npm test
npm run build
```

## Project Layout

- `src/index.ts` is the package's only entry point and must stay aligned with the public API.
- `src/ssh.ts` contains the unified `SSH` API (import, key generation, signing, certificates, thumbprints).
- `src/key/` contains `SshPublicKey` and `SshPrivateKey`; `src/cert/` contains `SshCertificate` and `SshCertificateBuilder`; `src/signature.ts` contains `SshSignature`.
- `src/wire/` contains the SSH wire format: `SshReader`/`SshWriter` and the public key, certificate and signature encodings.
- `src/algorithms/` contains the Ed25519, RSA and ECDSA bindings. `src/registry.ts` contains `AlgorithmRegistry` and registers the built-in bindings when the module is loaded.
- `src/crypto.ts` holds the WebCrypto provider (`getCrypto`/`setCrypto`); `src/errors.ts` and `src/types.ts` hold the error classes and shared types.
- `*.spec.ts` files sit next to the code they test. `*.compat.spec.ts` files check interoperability with the system `ssh-keygen`.
- `src/fixtures/` contains the key, certificate and signature fixtures, the fixture loader (`index.ts`) and the `ssh-keygen` helpers (`ssh_keygen.ts`). They use Node.js APIs, are imported only by specs, and are not part of the build.
- `build/` is generated by `npm run build` and is not committed.

## Development Workflow

### Code Quality

Before opening a pull request, run:

```bash
npm run lint          # oxlint
npm run format:check  # oxfmt
npm run typecheck     # tsc --noEmit
npm test              # vitest, runs once and exits
npm run build         # tsdown, also checks the package with attw
```

Fix lint and formatting issues with `npm run lint:fix` and `npm run format`. Use `npm run coverage` to produce a coverage report.

### Testing

- Use Vitest.
- Put tests next to the code they cover as `*.spec.ts`.
- Load fixtures through `src/fixtures/index.ts` and run `ssh-keygen` through `src/fixtures/ssh_keygen.ts`.
- Cover new behavior and bug fixes with tests.

### Build And Package Exports

The package is ESM-only; there is no CommonJS build, and CommonJS consumers load it through `require(esm)`. tsdown builds `src/index.ts` into `build/index.js` with `.d.ts` declarations and prepends the SPDX copyright banner. Output is unbundled, so every source module is emitted under `build/` mirroring `src/`, but only `build/index.js` is reachable through `exports`. The syntax target comes from `engines.node`; do not set `target` in `tsdown.config.ts`.

`exports` and the legacy `main`/`module`/`types` fields in `package.json` are generated by tsdown on every build and must not be edited by hand. To change the entry points, change `entry` in `tsdown.config.ts`, run `npm run build`, and commit the regenerated `package.json`. CI fails if the build changes `package.json`.

Use named exports only (no `export default`) and no top-level `await`, so `require()` of the package keeps working on supported Node.js versions.

`package.json` `sideEffects` lists `./build/registry.js`, the only module with import-time side effects (it registers the built-in algorithms). Register new built-in algorithms in `src/registry.ts`. If another module ever needs import-time side effects, add its built file to `sideEffects`; otherwise bundlers may drop it.

### Commit Messages

Use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). Pull requests are squash-merged, so the pull request title becomes the commit message and must follow the same format.

```plain
type(scope): description

[optional body]

[optional footer]
```

Types: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`, `style`, `revert`.

Mark breaking changes with `!` after the type or scope (for example `feat!: ...`) and/or a `BREAKING CHANGE:` footer.

### Pull Requests

1. Fork the repository and create a branch from `main`.
2. Make your changes, with tests.
3. Run the checks listed above.
4. Open a pull request with a Conventional Commit title.

## Code Style

- Write TypeScript.
- Follow the oxlint (`.oxlintrc.json`) and oxfmt (`.oxfmtrc.json`) configuration. Keep the lint config practical: prefer fixing the source over adding rules that only create churn, and disable a rule only when it fights the established style.
- Keep changes small and localized.
- Keep the library source free of Node.js-specific APIs; the package runs in Node.js and browsers on top of WebCrypto. Only specs and `src/fixtures/` may use Node.js APIs.
- Keep the algorithm registry a single module-level instance in `src/registry.ts`; every class that needs an algorithm looks it up there.
- Document every public exported type and function with concise TSDoc.
- Keep public exports stable; breaking changes need a major release.

## Releases

Releases are managed by [release-please](https://github.com/googleapis/release-please) (`release-please-config.json`, `.release-please-manifest.json`):

1. On every push to `main`, the **Publish** workflow first runs lint, format, typecheck, tests, and build (the **Test** workflow). Only when they pass does release-please open or update a `chore(release): vX.Y.Z` pull request that bumps `package.json`/`package-lock.json`. The version comes from the commits: a breaking change bumps major, `feat` bumps minor, and `fix`, `perf`, `build`, and `revert` bump patch. Other types do not trigger a release.
2. Merge the release pull request. release-please creates the `vX.Y.Z` tag and a GitHub Release with the notes from the pull request; the workflow then publishes that commit to npm via Trusted Publisher, with provenance, and moves the major tag (for example `v3`) when this is the newest release of that major.

To retry a failed npm publish, run **Publish** manually from the `vX.Y.Z` tag. Set the optional `RELEASE_TOKEN` secret (PAT or GitHub App token) so the Test workflow runs on the release pull request.

Release notes live only in [GitHub Releases](https://github.com/PeculiarVentures/ssh/releases); there is no `CHANGELOG.md`. Only `feat`, `fix`, `perf`, `build`, `revert`, and breaking changes are listed. Force a version with a `Release-As: x.y.z` line in a commit body. To fix the notes for a merged change, add a `BEGIN_COMMIT_OVERRIDE` … `END_COMMIT_OVERRIDE` block with the corrected commit message to that pull request's description; edits to the release pull request description are overwritten when new commits land.
